# Spec 治理：项目长期演进的最高依据

状态：生效。治理版本：2。生效日期：2026-09-26。
需求 GOV01 / U11：用户明确要求将spec维护优先级提升到最高，作为项目长期演进的核心锚点。

## 1. 权威顺序

在本项目需求、架构、语义、能力声明与验收范围内，按以下顺序处理：

1. 用户最新明确决定；将决定及影响同步进入spec。
2. 本治理规范及已生效spec要求。
3. 实现、测试、生成的Schema/OpenAPI、配置编译器及界面。
4. 操作README、临时计划、聊天总结、旧设计草案与归档材料。

此顺序是项目治理规则，不替代运行环境的安全或系统约束。Spec记录事实，不能覆盖原始证据或外部规则的真实变化；发现事实有误，应保留纠正记录并更新spec，不维持错误叙述。

代码或既有测试不因已经存在就获得高于spec的权威。不得为使当前实现“合规”而静默删减需求、放宽验收、抹去能力缺口。不同spec冲突时登记冲突，按明确的需求来源和变更记录解决；不得自行取较宽松条款。尚未解决时，不发布受影响的能力完成声明。

### 单一语义归属与文档交付（GOV03）

- 核心规范维护产品范围、稳定ID和跨域约束；细节各有唯一权威专题：代码结构与模块交接归ARCHITECTURE，采集编排/统一观察格式/质量报告归DATA_PIPELINE，人参与研究输入/评议/交接归HUMAN_RESEARCH，生命周期归RESEARCH_LIFECYCLE，交易归TRADING_BOUNDARY，比较身份/风险指标归RESULT_CONTRACT，验证算法与证据归VALIDATION，因子归FACTOR_ANALYSIS，进程执行归EXECUTION。其他文档引用，不重复维护另一套公式或判定表。
- 同一规则被替代时更新当前合同；旧定义进入有日期的历史说明或CHANGELOG，明确替代关系。历史审查、旧证据不重写，不能与当前条款并列生效。
- 产品目标、交互细节、缺陷修复分别组织；保留既有要求ID与追溯关系，不通过重排删除要求。
- 状态用语：**生效合同**是必须达到的目标，**已实现**表示存在实现但不自动代表已验收，**已验收**只覆盖注明版本/输入/环境的证据，**待设计冻结**表示不能直接照概述编码。未实现的生效合同仍有效，不得因实现不足而降级要求。
- 当前状态写明确核对commit；“与本条同提交”只允许用于首次交付，后续刷新当前索引时补齐commit。历史证据不改数字，误称或过期结论以带日期的勘误说明纠正；历史测试不提升为当前全量验收。
- IMPLEMENTATION集中记录当前状态及缺口；历史验证按批次保留，新增证据注明代码提交、spec/定义版本、范围与日期。没有在新基线上复验的旧证据不得称为最新验收。
- 用户明确要求仅刷新设计文档时，可单独提交spec；必须同时登记实现/API/测试尚未同步的差距和兼容计划，不得声称功能完成。后续实现须另行验证并同步交付。这不豁免实现变更时规范、代码与必要测试一起提交的要求。

## 3. 每次工作的强制顺序

### 开始前

- 阅读本入口、治理规范、核心规范、实施状态以及受影响专题。
- 确认需求ID、当前能力、缺口、用户最新决定及证据边界。
- 有需求/架构/口径/默认值身份变化时，先修改规范与决策记录，再实现。普通修复按现有spec执行，无需为了流程重复请求已授权事项的确认。

### 实施中

- 代码、配置、API、CLI和UI共同遵循spec；不能在某一界面单独计算或包装更强能力。
- 原生来源、派生计算、定制能力、模型意见、样本与缺失状态的语义变更，必须同步专题规范、接口及验收。
- 发现与规范不符的代码，修复实现；发现规范与事实不符，记录证据并纠正规范。不得先交付夸大表述再补文档。

### 交付前

- 更新IMPLEMENTATION中的真实范围、验证结果、剩余缺口；重要变更追加CHANGELOG。
- 检查文档间一致性、链接、需求到代码/验证的对应关系。文档变更本身可仅做结构/链接核查，不机械重跑无关测试。
- 新的能力声明必须有源产物或实测证据。仅有模板、Protocol、按钮、模拟样本或配置项不得标记完成。
- 实现已变更而对应spec、限制或验收尚未同步时，该项工作不得报告为完成。

## 4. 必须长期保护的约束

| ID | 不得静默退化的约束 |
| --- | --- |
| GOV-SOURCE | 行情性质与字段来源分别标记；手写样本不得伪装原生输出或参与研究排名；未知不填0 |
| GOV-DERIVED | 工作台计算要保留公式、输入来源、起止范围与缺口；观测回撤不冒充完整账户或原生超额回撤 |
| GOV-CLAIMS | 定制质量检查不冒充上游原生验收；通过检查不等于alpha有效；Agent意见与固定规则提示不能冒充事实 |
| GOV-CAPABILITY | 未接入、能力受限、未记录、失败与真实零值分开；进程成功、产物完整、研究质量分开 |
| GOV-HISTORY | 不可变结果revision和历史证据保留；不把当前配置/环境版本补写成历史运行事实 |
| GOV-UPSTREAM | Qlib与RD-Agent保持外部引擎/适配边界，定制不侵入上游核心；持续吸收上游改进时重验受影响合同 |
| GOV-CONFIG | 参数独立配置；用户指定值、账户假设、市场规则与工程默认分开；配置指纹不代替数据内容版本 |
| GOV-STORAGE | 只读核对不能触发原实验库迁移；MLflow审计使用只读源库副本；升级/迁移独立、备份、校验、保留恢复路径 |

这些约束可以随用户明确的新需求演进，但必须记录改动依据、兼容影响和替代保障，不能在重构、美化UI或合并上游时默默删除。

## 5. 变更记录与完成清单

重要变更在CHANGELOG中至少记录：日期、需求/问题来源、影响ID、决定及理由、实现范围、验证证据、已知限制、历史兼容/迁移影响。

交付核对清单：

- [ ] 已识别并读取受影响spec。
- [ ] 需求、口径或能力边界变化已先进入规范。
- [ ] 实现/API/UI/配置及测试与规范一致。
- [ ] 已区分事实、计算、假设、意见与未知。
- [ ] 完成声明有证据；历史记录和剩余缺口保留。
- [ ] 入口、实施状态、重要变更记录与链接已同步。

检查清单是交付门槛，不等于已建设自动CI门禁。当前为项目指令与人工/代理核查约束；自动化治理检查尚未实现，不能声称已由CI强制保护。

## 6. Git演进检查点 GOV02 / U12

用户明确授权：**每次重大修改完成后，commit并push一次**。这属于持续工作流程，不需要每轮再次确认。

- 重大修改包括需求或架构调整、spec治理、用户可见功能、数据/指标语义、来源及能力声明、依赖升级、数据库迁移。可紧密关联的实现与修正组成一个完整检查点；不为凑提交次数拆碎工作。
- 顺序：先同步spec → 完成实现 → 必要验证 → 检查diff与待提交文件 → commit → push到用户fork的origin工作分支 → 报告分支、commit和推送结果。
- 提交说明写清修改目的、关联要求及验证；同一改动的代码、spec、必要测试、脱敏摘要一起提交，避免规范与实现错位。
- 本机环境、密钥、数据库、模型文件、大型原生产物与运行日志不提交；脱敏证据摘要可以提交。
- 保留已有用户改动；不提交不相关或来源不明的更改。首次接管大量未提交成果时，核对范围后保存为现状基线，不伪造历史提交。
- 默认在现有工作分支提交，新增分支使用codex/前缀；推送用户fork的origin，不向upstream推送，不隐含合并主分支或部署。
- 不自动force push或重写已发布历史。推送失败先排查；无权限或需要用户解决的阻塞必须明确报告，保留本地commit，不谎称已同步。
- Git检查点未完成时，区分“实现已验证”“已本地提交”“已推送”；重大修改不得以未提交的本机文件作为最终交付。

## 全局一致性变更门（U31，2026-09-29）

每次新增/修改功能，必须沿ARCHITECTURE §0核对：上游输入身份和可用时间 → 本模块唯一写入职责 → 状态/事务/恢复 → 下游产物与复用失效 → UI能力与下一步 → 端到端反例。记录受影响要求ID及专题，不适用项说明原因；不能只更新新增专题后就宣称设计完成。共享概念只在指定主合同定义，专题引用；发现冲突要修改原生效条款并追加CHANGELOG，不以文末“覆盖前文”不断叠加平行规则。IMPLEMENTATION是唯一当前完成状态入口，审查报告保留日期/基线，不作为另一份实时状态表。

跨模块变更的验收须包含生产者到消费者的身份/语义验证；单个模块测试通过、目录分层或Protocol存在均不能关闭A45。规范详细程度分开声明：语义与归属已冻结，不等于物理DDL、完整DTO、迁移及适配器载荷已齐全；这些缺口必须经过已有设计门，不能由实现者自行猜测。
