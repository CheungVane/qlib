## 可维护性评价与取舍

- 已有可保留基础：bootstrap组合根、专职services、ports、外部引擎适配器、不可变结果revision、来源/能力边界和依赖门禁。真实快照→确定性基线→因子API/UI有独立证据，适合作为后续纵向切片的起点。
- 主要问题是共享语义尚未打通，优先级高于再拆几个目录。先统一Run与产物关系、输入准备、发布/恢复和能力判定，再让数据/研究/训练/回测使用它们。
- 个人项目继续采用模块化单体和少量固定流程；不引入微服务、通用DAG、动态插件市场或每个值对象一个服务。大文件按新增功能触及的职责分拆，保留兼容入口，禁止一边复制实现一边保留旧路径作为另一套事实。
- “低负担”需要用户能在页面理解输入、限制、进度、失败恢复和下一步；无需阅读spec才能辨别真实/模拟、探索/严格验证。ARCHITECTURE §0.4给统一页面上下文，A45-6要求完整使用验收。
