# 设计审查：2026-09-25

审查对象：旧版 `docs/architecture/quant-workbench.md` 与三份 prototype JSON Schema。基于本地源码和现有演示产物。下列问题均已在新 spec 中给出处置；不代表实现已经修复。

| 编号 | 问题与影响 | 证据 | 处置 |
| --- | --- | --- | --- |
| R01 | 把 Qlib 当成系统主体，新增目录仍可能共享依赖和全局状态，升级冲突并未真正隔离 | `qlib/config.py` 的全局 `C`；`qlib/workflow/__init__.py` 的记录器包装；根包属于 pyqlib | 工作台独立 Python 包；核心不 import Qlib/MLflow；执行适配器独立子进程，服务进程不初始化 Qlib |
| R02 | 一个 Run 必须选 training 或 backtest，不能准确表达一个 Qlib 工作流同时训练、生成信号、回测；queued 却必须有 started_at | `qlib/model/trainer.py::_exe_task` 依次调用 fit 和记录器；旧 run schema | Experiment、Run、Stage、Attempt、ImportReceipt、LiveSession 分开；阶段状态未知不推断；时间字段按状态约束 |
| R03 | 导入历史结果时，用当前环境版本和当前文件哈希冒充运行时版本会制造假的可复现性 | 原计划拟从本机环境取得引擎版本；旧 schema 强制所有版本已知 | 区分运行时证据、导入时观测和未知值；导入幂等键包含来源实例，不以当前环境补历史事实 |
| R04 | 统一市场数据主键过于简单，无法区分同一股票同一时刻的分钟线、报价、财务修订与公告 | 旧方案统一 instrument/event_time/source/version | 按数据种类定义键；证券身份与代码映射分离；区分事件时间、可用时间、入库时间和修订 |
| R05 | 指标只能绑定 run_id + 时间戳，训练 step 和系统错误率没有合理归属；缺数据与真零混淆 | 旧 metric-series schema 的必填 run_id/time、有限 frequency、可选 availability | 指标定义、主体、轴和观测状态分别建模；支持 step、time、scalar；单位和分母明确 |
| R06 | 只统一名称会错误比较年化收益、IC、成本后收益和净值；把所有差异都禁止对比也过严 | `qlib/contrib/evaluate.py::risk_analysis` 的日频频率缩放为 238；演示 SigAnaRecord ann_scaler 为 252 | 原生与平台标准指标分命名空间；比较区分展示、归一化叠图、可比排名，不强求不同策略费用相同 |
| R07 | “所有引擎都实现 submit/cancel”排除了只支持结果导入的框架；统一 UI 不等于策略可移植 | 旧 engine 接口定义 | ResultImporter 与 Executor 独立能力；能力分 supported/unsupported/unknown；策略执行语义由适配器负责 |
| R08 | SQLite、Parquet、对象存储拆开后缺少跨存储发布协议，崩溃可能留下半个结果 | 旧存储表只有技术名称和接口名称 | 先持久化不可变对象，后提交数据库清单；查询仅看已发布版本；幂等、孤儿回收和恢复纳入验收 |
| R09 | 元数据、时序、事件、各领域 Repository 同时上马，首版成本过高；换数据库不等于连接串替换 | 旧方案列了多种数据库但无语义边界 | 先本地单机；端口按用途分开，首版结果序列可与元数据共用 SQLite；大对象再用文件；云迁移要重新验收 |
| R10 | 所有页面都抽象为 dashboard widget，易损害运行详情、任务提交等固定交互；query 是无约束字符串 | 旧 dashboard schema | 固定领域页面 + 可组合总览；类型化查询注册表、筛选器、版本、布局校验；不允许任意 SQL/代码 |
| R11 | 实时和可靠性只列图表，没有迟到、重连、无样本、交易时段、状态采集等语义 | 旧实时/错误率描述 | LiveSession 独立；陈旧按交易日历和来源 SLA 判断；指标记录窗口、分母、采集覆盖；应用故障与连接故障分开 |
| R12 | 上游 MLflow 更新造成旧演示库无法读取，说明依赖回滚不等于数据格式回滚 | 本轮已出现 MLflow 高版本数据库对 3.12 不兼容，另建演示库才恢复 | 引擎版本、依赖锁和数据迁移独立管理；升级前备份，验证恢复；禁止对未知数据库自动迁移 |
| R13 | 费用口径和风控容易由演示默认值变成已确认产品规则 | `Exchange._calc_trade_info_by_order` 对合并费用取 min_cost；演示 16 只、8 持仓、日期等 | 单独标记用户要求、研究默认、演示参数；万二是佣金，其他税费/最低费为情景；无行业风控或回撤止损实现声明 |
| R14 | 只用 Qlib 验证解耦，无法证明 UI 不依赖 Qlib 的字段 | 旧实施顺序把多引擎放到很后面 | 第一阶段加入最小 engine-neutral JSON 导入夹具，通过同一服务与 UI 展示；真实第二引擎随后选择 |

保留的方向：继续使用 Qlib、CLI/UI 共用应用服务、来源与存储分离、保留原生产物、六类观察视图、版本化接口。主要调整的是语义边界、运行隔离、交付顺序和验收证据。

原三份 JSON Schema 与总览示例移至 `extensions/workbench/archive/prototype-20260925/`。它们此前没有消费者，当前不需要运行时迁移；不得作为新 API 的 v1 合同继续使用。
